Physical AI Learner Lab

I built this lab to follow one small robot from its MuJoCo model through control, simulated sensing, and wheel odometry. The tutorial grew out of places where my first checks were too shallow—and the fixes I had to make after watching a longer run.

Synthetic data

Rendered observations with a reproducible source

The dataset contains timestamps, 320 × 180 RGB frames, and depth values in metres. It is unlabelled simulator output; it is not real sensor data and no model is trained on it.

The depth contact sheet clips its color scale at 3.0 m to show nearby geometry and the room layout. The current macOS graphics backend reports limited depth precision without ARB_clip_control, so the values are presented as an illustration of the rendering pipeline, not sensor-grade measurements.

Try it

Start with the simulator on your Mac

MuJoCo runs natively on macOS; Docker Desktop is needed only for the optional ROS 2 Humble module. The setup script installs the hash-locked Python dependencies.

Run locally

git clone https://github.com/supashbhat/physical-ai-learner-lab.git
cd physical-ai-learner-lab
./scripts/setup_macos.sh
./scripts/run_lab.sh

Tested locally on Apple Silicon macOS with Python 3.13. The workflow also targets Intel macOS.

Follow the learning path

  • Inspect the robot's bodies, wheel joints, actuators, contacts, and camera.
  • Connect differential-drive kinematics to bounded wheel-torque control.
  • Compare wheel-integrated odometry with simulator truth.
  • Connect ROS 2 /cmd_vel to MuJoCo and publish /odom and /scan.

What testing changed

Small failures made the lab more honest

These are symptoms recorded while building the project, with the corresponding fix or limitation documented in the repository's troubleshooting notes.

“The first model command drove backward.”

The wheel-joint sign disagreed with the model's axis convention. A short startup check hid it; a five-second run and one-metre acceptance band exposed it.

“sim.time >= 5.0” failed at “4.999999999999671.”

Repeated 2 ms steps accumulated ordinary floating-point error. The test now uses a small time tolerance while still checking the run duration.

“Camera views swing down during acceleration.”

A height-only smoke check missed chassis pitch. A lightly lifted front skid now limits rotation, and a five-second tilt check guards the change.

Engineering approach

Physics, interfaces, and verification

  • MuJoCo XML model with actuated wheels, contact surfaces, obstacles, and a front camera.
  • Modular Python controller, simulation runner, odometry, sensing, and bridge components.
  • Token-authenticated TCP adapter with bounded commands, message limits, and a command timeout.
  • Hash-locked dependencies, fresh-environment setup, unit and integration tests, and a strict tutorial build.

AI-assisted authoring

AI assistance was used for scaffolding and drafting. I checked model behavior, commands, media, and numerical claims against runs and tests; when the first wheel-sign assumption failed, the model and acceptance test changed. The authoring log separates locally verified behavior from work that still needs an Intel Mac, Docker host, or learner feedback.

A concise project line

Built a macOS-first robotics learning lab in MuJoCo, with differential-drive control, wheel odometry, simulated camera and LiDAR, a ROS 2 Humble adapter, generated RGB/depth data, and a 20-test local verification suite.
